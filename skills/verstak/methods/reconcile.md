# reconcile — two-way reconciliation of code and graph

**Use when:** a material task is finishing (the main occasion), or you see code and graph diverge — out of failure 4 (the door, `The method fails in five ways`); the user asks — "reconcile", "check the code against the graph", "tidy the graph", "weave your area", "pay the graph's debts", "does the graph match the code"; or orienting shows tensions piling up in your area. Also on these signs: a one-off task recorded as a kriya; a state-label phenomenon; a wall-of-text comment retelling what belongs in the graph. Not `weaving` (repair from inside), `integrity` (claim audit), `reality-audit` (behavioural claims). Composes `entry`, `writing`, `weaving`.

The graph is a derived description of reality, most often of code, and a gap always opens: code moved on, the graph kept nodes whose referents are gone, comments retell what belongs in the graph. Reconcile closes it in both directions, within your own area. Work is finished not by the merge but by reconciling its trace: what the task made true, the graph says; what stopped being true, it no longer asserts. It follows done work — not scouting (`entry`), not design.

## Protocol — five passes

**0 · Stand in your holon and check the method.** `verstak_orient(realm=…, focus=<your holon>)` — boundary, kriyas, phenomena, calling vimarshas. Check which rules this graph follows (its canon, or ask the steward): tidying by invented rules is worse than dust. Other areas aren't yours: what you notice there goes to their steward as a vimarsha with `posed_to`, not an edit.

**1 · Forward pass: nodes against code.** Four questions per node:

- *Does what it asserts still exist?* For **external surfaces** (someone else's API, SDK, CLI, schema) this is real: vendors bump versions silently. Check by observation, not memory; didn't observe → lower the epistemic mode. Gone → `atita`; vanished without trace → `nashta`. **Delete only a record that carried no distinction** (a wrong-type node whose form lies — pass 2 — a duplicate, an empty concept); a false thesis is refuted and kept (`references/writing-modes.md`).
- *Does the name still match the code?* 正名, rectifying names: the code renamed the thing → rename the node, don't start a second.
- *Are the modes honest?* A claim nobody has checked against the code in a long time is at best `anumita`, not `pratyakshita`: check and raise, or lower.
- *Who pulls on it?* Ask **which kriya would break if this node disappeared**. None → a shelter, not a record (a `sinn` standing in for something that acts; a lone `context` arrow) — quiet detectors measure structure, not weight. Don't delete it blindly: a meaning without a carrier is rewoven into one (`upadhi` on the kriya that acts through it); storage without meaning → `atita`.

**2 · Telling a kriya from a task — the most common confusion.** The test (→ door, `One-off task`): ask the "kriya" what it consumes and produces on its next run; no answer → a task, lying by its type, its "result" degenerating into a state-label phenomenon nobody produces or depends on — an orphan by construction. Rewrite it: what it changed becomes transition nodes (the repeatable as a kriya, the result as a phenomenon a real kriya produces); re-anchor its vimarshas; remove the state-label phenomena with it; the unfinished becomes an assignment in a case on the subject's node. A large task with its own telos is a `bianhua`. Don't substitute a vimarsha for the task.

**3 · Reverse pass: code against the graph.** A wall-of-text comment — the reasoning behind a decision, rejected alternatives, how an integration works — is a graph node away from home: search won't find it, pass 1 won't touch it. Move the meaning into the graph and leave a **reference** in code: "(graph @owner/slug, node #N)". **Mechanics stay as words in the comment; meaning, reasoning and integration scope go to the graph.** "Close the socket before renameSync, or Windows throws EBUSY" stays; half a page on "why a queue rather than webhooks" moves. A reference goes where a reader without the graph couldn't understand *why*, not *how*.

**3a · Client inventory against edges — on a merge that touched a client module.** A call in the consumer's code without an edge breaks nothing in the graph and no gate or detector sees it, so call wiring is measured from outside: inventory the paths the client calls (parameters normalised; non-literal paths counted explicitly — a literal grep yields a sample and must say so), list the URL types your holon's kriyas hold `utpatti` on, and diff both ways. Three kinds: a call without an edge where the action exists → weaving; a call with no action → `methods/design.md`; an edge without a call → remove or mark removed. The inventory script lives in the consumer's repo and may gate CI; the remainder becomes vimarshas on their carriers. An integration-scope traversal of your holon promises coverage only between a zero-diff run and the next merge touching the client; outside that window it is a sample and is named so in the integration report.

**4 · Every option has three outcomes, all recorded.** The chosen one lives as decision nodes. A dropped one: a node in `visarjana`, reason in the body. A rejected one: `virodha`; one that survived a real dispute: a `prati-paksha` vimarsha, where later evidence can raise it. Code may reference a dropped option like a chosen one ("not cached: graph @owner/slug #N") — it leads to the reason as it stood. An unrecorded rejection is the costliest loss: the next agent walks into the same dead end in good faith.

**5 · Tensions and the close.** `verstak_orient(lens="tensions", focus=<your holon>)` — leaked, relay-gap, orphans: weave them now, while the context is hot (`methods/weaving.md`). Behavioural claims the passes raised ("`pratyakshita` again") go through `methods/reality-audit.md`. Close with a debt report — what was reconciled, moved, remains — the remainder as vimarshas on their carriers, not as a story: a debt told in chat dies with the session. Next moment: the debts are recorded → reflect on the method (`methods/feedback.md`).
